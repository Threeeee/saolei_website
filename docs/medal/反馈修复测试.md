# 勋章回归测试

本页维护可重复运行的测试命令与验收步骤。业务规则见[软件架构](./软件架构.md)，图片规则见[勋章图片](../../vitepress_doc/zh/guide/development/medal-art.md)。每次执行的日志和退出码保存在本地 `.tmp/checks/<轮次>/`，不把历史测试数量或某次尚未完成的检查状态作为当前结论。

## 自动回归

以下命令在 PowerShell 中运行。先启动本地 MySQL 和 Redis。Django 测试使用 `test_saolei` 测试数据库；排行测试也会操作配置的 Redis，请使用开发测试环境。

```powershell
cd back_end\saolei
.\.venv\Scripts\python.exe manage.py test medal identifier.tests.BindIdentifierServiceTest tournament.tests.test_reveal_video tournament.tests.test_reveal_transactions --keepdb --noinput
```

数据库必须与当前模型一致；模型变更按项目约定由 Django 自动生成迁移。录像补传时间修复没有新增或修改模型字段。

勋章测试按职责分组：`tests.py` 覆盖基础授予与规则，`test_queue_triggers.py` 覆盖信号和并发入队，`test_state_cache.py` 覆盖数据库进度及任务合并，`test_incremental_queries.py` 覆盖查询预算、展示回填和 Redis 故障，`test_cache_concurrency.py` 覆盖真实并发发布，`test_video_history.py` 覆盖补传和改时，`test_summary.py` 覆盖摘要事务，`test_overrides.py` 与 `test_staff_api.py` 分别覆盖人工决定服务和管理接口。共享夹具不应通过继承带有 `test_*` 方法的测试类复用，以免重复执行整组用例。

`test_refresh_status.py` 覆盖上传后状态查询的登录限制、本人隔离、READY/RUNNING/终态、补发任务和单次 EXISTS 查询预算。`medalService.test.ts` 与 `videoUploadService.test.ts` 覆盖上传成功才启动同步、批量合并、8 次请求上限、请求失败停止、无订阅时延迟读取以及旧悬停请求不得回填缓存。`UserMedals.cy.ts` 和 `PlayerName.cy.ts` 维护已挂载页面、佩戴栏和名字悬停的联动组件回归，组件测试按项目约定由用户明确要求后运行。

关键断言包括：

- 通过真实资料服务保存 `_realname` 后，在提交时入队。
- 绑定、解绑和比赛公开保留批量更新，并按玩家去重；回滚不入队。
- 同一玩家并发入队只产生一条同类 `READY` 任务；已运行任务允许再排一次刷新。并发测试需要 MySQL 行锁支持，SQLite 会跳过。
- 已有 READY 任务的执行时间异常过晚时，新录像合并会将时间提前到当前 3 秒延迟上限，历史补发提前到当前时间；正常较早时间不推迟。worker 在合并查询之间领取任务时，另建 READY 任务，不能丢失新录像。3994 ms → 2484 ms 的保存信号、任务执行、Sub4 → Sub3、证据和阶段日志、摘要及展示缓存一起验证。
- 最佳成绩仍为 19 秒时，把门槛从 20 秒收紧到 10 秒会撤销，放宽可重新授予。
- 旧授予证据被删除或冻结、仍有其他达标录像时，替换证据，不依赖最佳录像指针。
- 旧版最佳字段在下次评估中清空，摘要提前隐藏旧最佳值。
- 同档、升档和批量补传按最早有效证据校正日期及日志；上传时间改早或改晚，都同步修正数据库、摘要和状态缓存。
- 历史低档证据变化时保留正确的当前高档证据；阶段节点去重、排序，重复刷新不追加重复节点。
- 新手集合与三阶勋章保留全部分项证据，非最后完成分项改时同样重新计算完成时间；人工锁定结果不受自动修正影响。
- 已获得的新手、股东、复合勋章及 PB 均无变化时，不产生业务 `INSERT` / `UPDATE` / `DELETE`，进度只读取一次。
- 热图鉴读取不查询数据库；玩家摘要已经建立且图鉴缓存命中时，热摘要为1次业务查询。能力勋章同档 48 秒提高到 46 秒时，增量和全量刷新均不产生勋章业务写入；升到 Sub40 时追加阶段并换证据。这些是测试断言，不是生产耗时承诺。

## 数据库增量与查询验证

```powershell
cd back_end\saolei
.\.venv\Scripts\python.exe manage.py test medal.test_incremental_queries medal.test_cache_concurrency medal.test_video_history --keepdb --noinput
```

普通已初始化玩家、已有集合完整且不发生勋章变化时，捕获 SQL 并断言 6 次 SELECT：用户及摘要/佩戴/扫描、本次录像、有效定义、用户进度、授予及关联证据、人工覆盖。事务控制语句不计入 SELECT，另断言没有勋章业务写入和 Redis 访问。多条录像合并仍为 6 次；Redis 缺失、空值或含错误计算字段不影响结果。历史查询仅在需要时增加，固定补传 fixture 断言 11 次 SELECT，并验证每条历史录像查询限定该用户、取最早单条证据。

展示缓存命中时 0 次业务 SQL；多个玩家缺键且摘要齐全时共 1 次 SELECT，摘要缺失时共 2 次，均不查询历史录像。内部模式集合改变与仅修改佩戴不发布名字缓存。Redis 发布失败时仍提交数据库，尝试删除旧缓存；读故障回落数据库，后续读取可回填。事务回滚不发布，延迟的旧回调必须读取最新摘要。MySQL 真实双连接测试还验证：冷缓存回填持有玩家锁直到发布完成，随后升级的回调最终写入新档位。

2026-10-25 本地对比使用同一 MySQL 测试库及本机真实 Redis（随机独立键前缀，完成后清理测试键），分别预热 3 次，再交替运行改造前后各 20 次；比较授予档位、时间、证据与完整阶段日志一致。范围为 `refresh_player_medals` 及手动执行的提交回调，不含录像保存、任务入队和任务框架，耗时包含 SQL 捕获开销。结果记录在 `.tmp/checks/medal-db-incremental/benchmark-redis-results.json`，原始查询按场景另存；该目录不提交。

- 普通无变化：SELECT 14 → 6；耗时中位数 8.683 → 3.982 ms，P95 12.871 → 4.255 ms。
- 展示缓存缺失：SELECT 32 → 6；耗时中位数 21.204 → 3.995 ms，P95 21.676 → 4.433 ms。旧实现退回全量，新实现保持增量。
- 更早录像补传：SELECT 18 → 11；耗时中位数 13.973 → 10.559 ms，P95 15.253 → 11.156 ms。
- 升档：SELECT 18 → 11；耗时中位数 14.290 → 10.930 ms，P95 16.267 → 11.487 ms。
- 修改当前证据时间：SELECT 18 → 11；耗时中位数 13.515 → 10.215 ms，P95 13.894 → 10.670 ms。

这些特殊场景的次数与达标勋章、已记录阶段及分项数量有关，11 次只适用于上述 fixture。耗时属于本地小数据实验，没有模拟生产网络、完整 COMMIT 和锁竞争，不能作为生产时延或吞吐承诺；生产仍应观察接口 P95、SQL 耗时、任务等待时间和 Redis 命中率。

## 浏览器验收

按根目录本地启动说明启动后端、前端和 `manage.py db_worker_robust`。打开 `http://localhost:8080/#/player/<玩家ID>/medals`，在开发者工具 Network 中筛选 `/api/medal/players/`。

`db_worker_robust` 是独立进程，不会随 `runserver` 自动启动或重载代码。修改后端任务代码后需要重启 worker。勋章不变化时先检查 READY 任务的 `run_after`、任务错误和 worker 存活状态；不要只看残留 PID 文件。数据库和 Redis 已更新但当前页面仍显示旧值时，使用“重新加载”按钮或整页刷新读取新结果。

1. **首次补发**：选择已有录像但尚无 `MedalScan` 的测试玩家。页面先显示历史勋章补发提示，响应 `scan_pending=true`。工人完成后，后续请求应返回 `false`，页面无需重新进入就显示结果。侧栏与页面同一时刻只发一次摘要请求。
2. **工人未启动**：在首次扫描前暂停测试工人。页面每 2 秒尝试一次，最多自动重试 10 次，然后停止；点击“重新加载”可重新开始有界重试。启动工人后再次点击，应恢复并自动显示勋章。这里的状态仅表示首次扫描，不表示之后每个刷新任务的执行状态。
3. **切换玩家**：开启网络限速，快速从 A 切到 B。即使 A 的响应较晚到达或失败，侧栏和页面都不能显示 A 的勋章、清空 B 的结果。
4. **切换标签**：同一玩家在 30 秒内切换其他个人页标签再返回，应复用摘要；勋章页被 KeepAlive 停用后，不因玩家变化而自行请求隐藏页面的数据。侧栏仍显示时，它自己的订阅可以继续工作。
5. **保存佩戴**：调整佩戴并保存，侧栏和页面同步刷新；其他玩家的摘要不应因此重新请求。
6. **实名与批量操作**：使用测试账号修改实名、绑定/解绑含录像的标识，以及公开已颁奖比赛录像。等待工人处理后重新加载页面，确认对应新手、PB 勋章授予或撤销。绑定/解绑整批录像应只为该玩家排一次待执行刷新。
7. **规则与证据**：在测试数据中调整 PB 定义阈值，或冻结仅用作授予证据的旧录像，再调用玩家刷新或管理员补发。等待任务完成并重新加载摘要，确认档位、撤销状态和证据更新。自动测试已覆盖这一组，不必手动修改真实玩家数据。
8. **补传与改时**：对已有勋章的测试玩家补传更早的达标录像，或保存更早、较晚的 `upload_time`。无需管理员手动刷新；等待保存信号触发的任务完成后重新读取摘要，确认日期、证据及日志一致。修复部署前已经存在、以后没有再变化的错误记录，可通过本人刷新或管理员重算接口触发一次全量核验。

新增或替换图片后运行 `front_end/scripts/test_medal_art.py`；当前发布资源为每个系列一张透明 WebP 底图，尺寸、编码和体积预算统一维护在[勋章图片](../../vitepress_doc/zh/guide/development/medal-art.md)，不在本页复制这些参数。
